# Development and release

Maintainer documentation for Unqlock. User-facing documentation is in README.md.

## Build

Requirements, build commands and manual installation of a local build are in README.md under Building from source. Run every command from the repository root.

Beyond the outputs listed there, npm run sign:firefox writes artifacts/unqlock-firefox-VERSION.xpi when Mozilla returns a signed file, and npm run package:source writes artifacts/unqlock-source.zip, the archive listed AMO submissions upload for review.

Unqlock is TypeScript built with WXT, which runs Vite once per browser. wxt.config.ts holds the manifest, with the Chrome and Firefox differences chosen by browser, and keeps both on Manifest V3; the version comes from package.json. Entrypoints live in src/entrypoints: the background, one file per content script (`<name>.content.ts`, or a `<name>.content/` folder when it brings CSS), and the popup. Each content script still builds to its own file under content-scripts/, which the browser tests inject into their fixtures. The builder content scripts and MAIN-world bridges are declared for every unqork.io page, because Unqork's module search can reach the builder by rewriting the URL of a page that started outside /ide/ and browsers inject only for the URL a page first loads; src/lib/builder-route.ts holds each one back until the route first reaches /ide/, comparing only the path until then. Shared models in src/lib are plain modules imported by whichever entrypoint needs them; src/lib/api.ts chooses Firefox's promise-based browser API when available, otherwise Chrome's. No polyfill is needed. React and React DOM are the only runtime dependencies, bundled into the popup alone. Both packages contain identical JavaScript, CSS, HTML and icons; only manifest.json differs.

Build tools are development-only. ZIP files contain no npm packages or tests. scripts/build.cjs runs WXT for each browser into dist/<browser> and zips the result with fixed timestamps and sorted entries, and it refuses symbolic links or redirected output directories. The bundles are left unminified for store review, and wxt.config.ts turns off the bundler's debug comments, which would otherwise embed absolute source paths and make a build depend on where the repository is checked out. Isolated content scripts set `noScriptStartedPostMessage`, so WXT's start-up notice is not broadcast to the page's own message listeners.

## Add-on identity

The add-on ID is unqlock@fusan.me. Keep the ID unchanged for subsequent releases.

The popup is one React app, src/entrypoints/popup, rendered by the same page in the toolbar popup, the floating-menu iframe and detached windows. src/popup/App.tsx resolves which of those it is (src/popup/runtime.ts), then nests four providers: `PagesProvider` (src/popup/pages.tsx) is the only navigation code. `open(id, origin)` and `back()` show one page at a time, the page title takes focus on open, the originating control regains it on return, and `usePageOpen` and `usePageLeave` hooks hold a page's load logic and let it keep itself open, as Debug tools and Import & export do to let Escape dismiss a pending confirmation first. On the home menu of the floating launcher, Escape closes the menu. `SettingsProvider` holds appearance, row layout, toolbar and color settings with one save, so the home and page copies of a preference (`AppearanceToggle`, `data-appearance="key"`) share one value; a save shows the change at once, then writes it. Reset style and Reset layout each write only their own keys. `EnvironmentProvider` owns the environment configuration, the target tab and the background's `environment.*` messages for the home strip, Environments, Floating launcher and Import & export. `DebugProvider` holds Debug tools' target, site access, confirmation and execution, shared with Log page data on the home menu. Each page is a view in src/popup/views built from the components in src/popup/components: `Page`, `FeatureEntry`, `Toggle`, `Segmented`, `Select`, `TextField`, `Button`, `Card`, `Tabs`, `Note`, `Status` and `PageFooter`. `Unavailable` wraps any control that can be disabled with a reason, giving it a focusable "Why … is unavailable" wrapper and tooltip; once wrapped, a control keeps the wrapper so it is not remounted, and controls that listen for native `change` events (color swatches, panel widths) attach them through ref callbacks for the same reason. Import & export (with the pure model in src/lib/settings-transfer.ts) groups storage into the same sections as the pages; an import validates the whole file, writes only the chosen sections and sends environments to the background as `environment.save` with `replace`, so custom-domain registration stays in one place. Canvas layout also holds the Toolbar options, stored as `canvasToolbar` (src/lib/toolbar-settings.ts) and exported with the Canvas layout section. The canvas-toolbar content script clicks Unqork's own search button whenever it is rendered and returns focus to the element that had it; it stops after six clicks in two seconds if the field does not open, until the next module or settings change. Both scripts watch the page only while their option is on. While the field is always visible, it intercepts Close search and Escape in the capture phase and clears the field through the native value setter and an input event, so Unqork's state empties without the field closing; Escape on an empty field only blurs it. It passes the sort choice to MAIN as `data-unqlock-sort-mode` on the root element. The canvas-toolbar bridge runs in MAIN, walks up from the sort trigger's React fiber to the component whose props hold `options`, `selectedValue` and `onSelect`, and renders the switches beside the hidden trigger, calling `onSelect` on click. React keeps two versions of each fiber, so the bridge reads props from the current one using the same pairing walk as React's findCurrentFiberUsingSlowPath; the fixture's memoized trigger keeps the switches honest about reading the value from the dropdown rather than the trigger. Any other shape leaves the native dropdown alone. The environment-label toggle on Floating launcher saves `environment.badge` through the background's partial-preference merge. Floating launcher's Position choice saves `floating.mode`, `fixed` or `draggable`, beside the corner in `floating.corner`. Versions before these modes saved the corner as `floating.position`, so `floatingSettings()` falls back to it for stored settings and old exports, and the next save writes `corner`; Corner is unavailable under Draggable, which starts from the saved corner (bottom left by default). Under Draggable, the badge content script captures the pointer on press and treats a move of 5 px as a drag, skipping the click that ends it. The drop is anchored to the nearer edges of its screen quarter and saved with the corner it came from in the page's `sessionStorage` (`unqlock.launcherSpot`), so it lasts for the tab and is dropped when Fixed is chosen or the corner changes; it is kept 8 px inside the window on resize. One placement function sizes and places the menu frame for corners and dragged spots alike: it opens toward the side with more room, up to 600 px tall, starts at the launcher's nearer edge and is shifted to stay 16 px inside the window. `tests/environment-browser.cjs` covers dragging, the session spot across a reload, menu placement and a smaller window.

Commit the files shown above, including the PNG icons and package-lock.json. Do not commit node_modules/, .wxt/, dist/ or artifacts/; they are generated locally and ignored by Git. Build scripts resolve paths from their location, so they do not depend on a machine-specific checkout path.

## Tests

```sh
npx playwright install chromium firefox
npm test
npm run lint:firefox
```

npm test runs scripts/test.cjs, which runs the groups in scripts/test-groups.cjs in order: the type check and Vitest unit tests first, then the build, then the browser suites against dist/. Pass group names to run only those, such as `node scripts/test.cjs build chrome`; every group after build needs a current dist/. CI runs the build group in its build job and every other group as its own parallel job, listed by `node scripts/test.cjs --matrix`, so the run page names the failing group, and in Actions each test's output is folded under its title with its result and time. Each group lists the Playwright browsers it needs, and its job installs only those. tests/build.cjs fails if the workflow stops deriving its test jobs from that list. npm run test:unit runs only the unit tests. npm run lint:firefox runs web-ext lint through scripts/lint-firefox.cjs, which fails on any error or warning except the two innerHTML assignments inside React DOM, which exist only for dangerouslySetInnerHTML; Unqlock never uses that, and a third such warning fails the lint so new code gets reviewed. The unit tests in tests/unit render the real React popup in jsdom with an extension API double, once under `chrome` and once under `browser`, so both API branches are covered: `harness.tsx` installs the double and imports a fresh copy of the popup for each run. They interact through Testing Library's `fireEvent`, which sets values the way React expects; assigning `.value` and dispatching an event by hand does not reach a controlled input. Tests that run code outside the built extension, such as model checks and page actions, bundle it from src/lib with esbuild through tests/lib.cjs; tests that inject content scripts into fixture pages read the built files from dist/<browser>/content-scripts.

Optionally set CHROME_PATH to an installed Chrome for Testing executable for the Chromium tests. Otherwise Playwright's Chromium is used. Tests run in isolated profiles using synthetic builder fixtures and do not access your real module data. The Firefox behavior test supplies a browser API test double; it verifies Firefox rendering and the Firefox API branch, not Mozilla signing or live-site permission prompts. An additional web-ext test installs and reloads the actual Firefox package in an isolated temporary profile (optionally set FIREFOX_PATH to override its executable). Chrome integration loads the actual unpacked extension and exercises persistent popup settings, page navigation and focus return, the bound home switches, the split resets and logging from home. No tests install an extension into your normal browser profile.

The behavior fixture mirrors the builder's canvas markup as captured from a saved builder page: a header with an icon tile, an identity wrapper holding the property ID and type label, and a trailing group with the dependency count, actions menu and container chevron, plus collapsible containers built from `data-slot` collapsible triggers and content. Canvas row layout and the container options detect exactly that structure and leave anything else untouched, so update the fixture first if Unqork changes it. Unqork's legacy canvas view changes two shapes. A labeled component's header shows the label as its name and `key · TYPE` as its type line, so the type is read after the last `·` or `•`. Whenever canvas components are styled, the content script also stores the two parts on that line as `data-uq-legacy-id` and `data-uq-legacy-type` (only when the ID matches the row's key), and style.css hides the original text and draws them with `attr()`: the ID muted in Unqork's `--muted-foreground`, shrinking first, then the type, which keeps the type color and, under compact, the badge. Unqork's theme variables are `--muted-foreground`, `--color-foreground`, `--color-background` and `--color-border`; there is no `--color-muted-foreground`. Inputs, buttons and content become previews with no icon tile, property ID or type, only the preview and the actions menu. For those, the canvas-components bridge (src/entrypoints/canvas-components-bridge.content.ts) runs in MAIN, finds the React node a few levels above each `[data-component-key]` row whose `component` prop has the same key, and copies its `type` and `label` onto the row as `data-unqlock-type` and `data-unqlock-label`, falling back to `title`, where field groups keep the label shown in Properties; the content script uses the type when the row shows none, and watches that attribute. A preview row takes only the row-wide effects (accent, background, border, and its chip and actions colors); icon, tile, label, compact and row-layout marks need the header it lacks, and its first icon is the actions menu's. A container's header is nine levels below its node, so the search goes up to twelve. The bridge also marks a row `data-unqlock-legacy` when its node's `renderPreview` prop is true, which is how Unqork tells its legacy view apart; a row whose label equals its ID looks the same in both views. Component labels (`canvasLabels`: `native`, `different` or `always`, src/lib/label-settings.ts, exported with Canvas layout) draws `data-unqlock-label` after the property ID. The content script copies it onto the name line as `data-uq-component-label` when that line shows the property ID and `Labels.shows` allows it: When different adds only a label that differs and none in the legacy view, which already shows it; Always adds every label, in the legacy view only those that repeat the ID. style.css renders it with `attr()` in a `::after`, so Unqork's markup gains no nodes. A label edited in Properties changes nothing in a row that shows the ID, so the bridge also runs on `input` and `change` events and polls once a second while the page is visible. The behavior test covers both shapes, the label mark and an edit, and runs the built bridge against a stand-in fiber. Group colors live in src/lib/component-colors.ts: the default palette, the picked colors stored as `componentColors` (`{ group: { light: { ink, tint }, dark: { ink, tint } } }`, picked values only), and the partner rule: a theme with only one picked color derives the other, a background capped short of white or black so it keeps its hue, or a foreground with at least 5:1 contrast. Two picked colors are used as picked. A derived pale background cannot keep close hues apart, which is why backgrounds can be picked. The content script's style.css only references variables; the content script (src/entrypoints/content.content) sets them, and the distinct-shape images built from the palette, on the root element through the CSSOM, which the builder's content security policy allows where an injected stylesheet might not. On a colored surface, a full-background row or a tinted container header, the content script also marks the row's own dependency chip (`data-uq-chip`) and actions menu and chevron (`data-uq-row-control`) so they take its colors instead of Unqork's brand tint and gray; tinted headers use the background color and keep a 12% foreground band over full backgrounds. Unqork rings the selected row and search matches with `ring-unqork-brand/70` and `ring-amber-400/70`, classes its stylesheet never generates, so both fall back to a ring in the text color; style.css gives styled rows those rings in the brand and amber colors, opaque and wider than a group border, matches a full border to them, and restores the amber background of the current match (`ring-amber-500`) under full backgrounds. Recheck those class names if search or selection highlighting stops showing. The Colors section of Component style renders one picker row per group from the same module. The content script reruns only for mutations that touch a component or an element it marked, or after a route change; the rest of the builder, such as streaming Build Agent replies, changes on nearly every frame, and a full pass costs about 5 µs per component.

In the live builder, the bridge finds the public panel reference at depth 1 for all four side panels, resizes each one and restores original widths and collapsed state. Recheck this against Unqork's current builder before a release, since it depends on their integration.

Always collapsed guards the native public `expand` and `resize` methods in MAIN. Accessors retain native method replacements during rerenders and restore the latest implementation on unlock. The bridge collapses once through the native API, avoiding repeated close-button clicks when component selection requests expansion. If the builder no longer exposes configurable public methods, the existing close-after-reopen behavior remains the fallback. The panel tests sample widths across animation frames and check rerenders, all four panels and restored expansion; the installed Firefox bridge test covers the actual world boundary.

The navigation-tabs content script hides Unqork's tab bar, `nav[data-testid="navigation-tabs"]`, while `navigationTabs` (src/lib/panel-settings.ts, exported with the Builder panels section) is `hidden`. It does this through a root attribute and its style.css, and it watches the page only while the bar is hidden. Unqork keeps open tabs in its zustand workspace store and saves them to `localStorage["ide-workspace-store"]`, which it flushes on pagehide. Writing that storage directly would be overwritten, so instead the script clicks Unqork's own `Close … tab` button on every `[data-sortable-tab]` that does not hold the active `a[data-active]`, after first opening collapsed group pills so their tabs render. Unqork closes a tab that is not the current route without a dirty check, because its navigation guard already handled leaving it; the script never touches the current tab. A tab or group clicked three times without going away stops the script until the next route or settings change. While hidden it also repeats the current tab's application (its group pill) and module label, with the tab's icon, in the toolbar row: the element marked `data-unqlock-module-title` goes between the two `flex-1` spacers after the `Select view` selector, and is left out if the row has another shape. Its attribute holds the rendered text, so the mutations it causes change nothing. Multi-line (`wrapped`) keeps every tab and lets the bar grow to the tallest one. Unqork shortens a long name in the label text itself, cutting out its middle, so wrapping alone cannot show it: the script places a `data-unqlock-tab-name` span holding the name from the tab's close-button label after Unqork's label, which style.css then hides, and redraws the active tab's shape in CSS at the taller height: Unqork's is a 33px SVG that would distort if stretched, so it is hidden and replaced by a body with 12px top corners inset 12px on two radial-gradient flares, in Unqork's `--color-background` and `--color-border`. `navigationTabsCollapsed` collapses the bar under Default and Multi-line, and the script keeps it apart from Hidden, which ignores it without clearing it. While it applies, the root carries `data-unqlock-navigation-tabs-collapsed` and the script shows the toolbar title as for Hidden, taking every name from the close-button label so it is never Unqork's shortened text, but closes no tabs. style.css takes the bar out of the layout as an overlay at the top of its parent and shows it through `:root:has(…)` while the `header` or the bar is hovered, the bar holds keyboard focus (`:focus-visible`, so a clicked tab does not keep it open) or one of its menu triggers is expanded. Visibility switches only after the fade, so the bar can still be reached while it closes. Unqork sizes groups, pills and tabs at `h-full` of the 40px bar; once the bar's height comes from its content, as under Multi-line and especially in the collapsed overlay, those percentages fall back to each element's own height and the application pill sits at the top. Multi-line sets them to `height:auto` so the bar's stretch alignment sizes them all to the tallest tab. The fixture copies that layout in a small stylesheet so the test catches it. `tests/navigation-tabs.cjs` runs `tests/fixtures/navigation-tabs.html`, a copy of the captured markup that persists its tabs the same way, against the installed Chrome extension and the Firefox API branch. Recheck the selectors against the live builder before a release.

Detach dev overlay is an opt-in Debug tools option, `devOverlayDetach` (src/lib/dev-overlay.ts; not exported, since Debug tools has no Import & export section). Its two scripts use WXT's `registration: 'runtime'`, so neither is in the manifest and WXT adds no host permission for them; the background registers them with `scripting.registerContentScripts` (`persistAcrossSessions`) for `https://*.unqork.io/*` only while the option is on and that origin is granted, reconciling on the storage change, grants, revocations, startup and install. Chrome does not extend the access the manifest's content scripts hold to registered scripts, so the switch requests `https://*.unqork.io/*` from `optional_host_permissions` (a prompt, since it is a new grant) before saving, and removes it when turned off; where the popup cannot show that prompt, as in Firefox, it asks in the prompt window, which saves the option once access is granted. Turning it on also injects the isolated script and its CSS into open builder tabs; it marks the root `data-unqlock-dev-overlay` so a second injection does nothing, and it watches storage so turning the option off removes its buttons from open tabs. The dev-overlay content script adds **Detach dev overlay** before Unqork's `Minimize dev overlay` button in the header of its bottom drawer, `[data-testid="dev-overlay"]`, which holds the SSE Debugger; style.css gives the added button `margin-left:auto` so the row's `justify-between` keeps it beside Minimize. Detach opens the current URL with `window.open` under the window name `unqlock-dev-overlay` (`detachedName` in src/lib/builder-route.ts), sized from the drawer, then clicks Minimize. Moving the live overlay into another document was rejected: React's root event listeners, Base UI's portals into `<body>`, document-level Escape and outside-click handlers and the editors all belong to the original document. The popup is instead a second complete builder, so everything works natively, at the cost of its own in-memory debugger state (`useDebuggerStore` persists only `ide-sse-debugger-identity`). The name survives the popup's reloads, `isDetached()` reads it, and `whenIde` starts nothing there, so every builder script stands down; the overlay script instead sets `data-unqlock-dev-overlay="detached"` on the root, where style.css pins the drawer to the whole window and hides `dev-overlay-toolbar`, `dev-overlay-drag-handle` and Minimize, clicks `Expand dev overlay` (at most three times) because the main tab saved the drawer minimized, prefixes the title with `Dev overlay · ` and puts **Reattach dev overlay** in Minimize's place, which closes the window. The main tab polls the popup's `closed` once a second and expands its drawer when it closes, so closing the window any way reattaches without cross-window messages; a reloaded main tab loses the reference and stays minimized. The dev-overlay guard runs in MAIN at document_start, only in the popup, and drops `localStorage` writes to `ide-workspace-store` and `ide-dev-overlay`, so the popup's stale tab list, flushed on pagehide, and its full-window drawer never overwrite the main tab's; other keys, such as the Run as identity, save normally. `tests/dev-overlay.cjs` runs `tests/fixtures/dev-overlay.html`, a copy of the captured drawer whose Run as list portals to `<body>`, against the Chrome extension and the Firefox API branch. The Chrome run loads a copy whose manifest already holds `https://*.unqork.io/*`, so the switch's request resolves without a prompt, and covers off by default, injection into an open tab, registration on reload and removal; `tests/environment-background.cjs` covers registration against grants and revocation, and `tests/unit/debug-tools.test.tsx` the switch. In Firefox, Playwright runs a popup's init scripts in its first about:blank document, so the test injects the isolated script once the popup is parsed. Recheck the `dev-overlay` test IDs and the Minimize and Expand labels against the live builder before a release, and that Unqork does not object to the module being open twice.

The prompt window, `prompt.html` (src/entrypoints/prompt, views in src/popup/prompt), asks for site access and picks settings files where a popup cannot: Firefox closes its toolbar popup when a permission prompt or file picker opens, and a floating menu frame may lack `permissions.request`. `promptWindow()` in src/popup/access.ts decides, true in Firefox or without that method, and `requestAccess` either shows the browser's prompt directly or sends `prompt.open`. Debug tools keep `debug.permission`, which checks the page first and opens the window with `kind=debug&tab=…`; Detach dev overlay and custom-domain badges send `prompt.open` with `kind=devOverlay` or `kind=badges`, and the Firefox toolbar's Choose file with `kind=import`. The background opens it with `windows.create` as a popup window sized from src/lib/access.ts, and adds the asking floating menu's tab when there is one. The page is not web accessible, and its address names only the kind and tab: it asks the background with `prompt.describe` what to request, so a crafted address cannot widen the request (debug resolves and checks the tab's configured page, Detach dev overlay asks for `https://*.unqork.io/*`, badges for the saved custom domains still missing). **Allow access** calls `permissions.request` before any await, as Firefox requires, then sends `prompt.granted`; the background acts only on a grant the browser holds, and finishes the request itself, since a Firefox toolbar popup has closed by then: it saves `devOverlayDetach`, re-registers and injects custom-domain badges, and sends `access.changed` to the asking tab, whose badge script passes `unqlock.accessChanged` to its menu frame. `useAccessChanged` hears that, or `permissions.onAdded`, so Debug tools and Environments update in place; Detach dev overlay follows its storage key. The import view reads, reviews and imports through src/popup/transfer.ts, the same steps Import & export uses, and environment messages accept the prompt page as a sender. `tests/unit/prompt.test.tsx` covers both views, `tests/environment-background.cjs` the messages, sender checks and finishing, and `tests/prompt-window.cjs` runs the window against the installed Chrome extension with unqork.io access already granted in a test copy of the manifest.

What's new (src/popup/views/WhatsNew.tsx), opened from the link beside the version in the header, which is why `PagesProvider` wraps the header as well as the pages, shows `releases` from src/lib/whats-new.ts, the notes for every version from 1.0.0, newest first. Each keeps the wording it shipped with, even where it names a popup that has since changed, and a note's optional `page` links only to a page that still holds the feature; text takes `**bold**` and `*italic*`, rendered as elements. Versions 1.0.0 to 1.1.0 had no release notes and were written afterwards from their commits. `whatsNew` in storage holds `seen`, the version whose notes were last read or dismissed, and `badge`; it is not exported. On install the background sets `seen` to the installed version; on update it keeps a stored `seen`, or starts from `previousVersion`, which is how versions before What's new, which stored nothing, are handled. It turns `badge` on, and the toolbar's *NEW*, when a minor or major release after `seen` has notes, and restores the badge on startup. Opening the popup turns `badge` off; `WhatsNewProvider` (src/popup/whats-new.tsx) shows the home notice until the page opens or the notice is dismissed, both of which set `seen`. A missing `seen` counts as nothing unread, and notes for a version above the installed one are not shown, so the next release's entry can be written ahead. `tests/unit/whats-new.test.tsx` checks the order, page links and that docs/RELEASE-NOTES.md names the newest entry and each of its titles, and drives the notice and page in both API branches; `tests/whats-new-background.cjs` runs the built background through installs, updates and restarts.

To edit the extension icon, change src/public/icons/unqlock.svg and run npm run icons after installing Playwright's Chromium. This regenerates the committed PNG icons and the documentation preview. Regular builds use the committed images and do not need a browser installation.

The component catalog in docs/component-catalog.json is used by the behavior tests.

docs/PRIVACY.md is the privacy notice both store listings point to. Keep it consistent with the permissions the manifest declares.

## Versioning

Version bumps are manual: patch for fixes, minor for features, major for breaking changes. The helper updates package.json and package-lock.json together without committing or tagging. Both browsers always share one version. Numeric major.minor.patch versions only; prerelease suffixes are not supported.

Example next patch release from 1.0.0, run after committing other changes:

```sh
npm run version:bump -- patch
npm test
npm run lint:firefox
git add package.json package-lock.json
git commit -m "Release 1.0.1"
git tag -a v1.0.1 -m "Unqlock 1.0.1"
git push origin HEAD
git push origin v1.0.1
```

Use minor, major or an explicit higher version instead of patch as needed; adjust the commit and tag accordingly. Run npm run version:check -- v1.0.1 to verify a proposed tag. Do not move published tags; fix issues in a new version. Both stores reject a version they already hold, so a rejected or superseded submission needs a new version.

## Continuous integration

Every push and pull request runs on Ubuntu with Node.js 22. The build job validates a release tag, runs the build group, Firefox lint and source packaging, and uploads dist/ (kept one day) and the ZIPs (kept 14 days). Then one test job per remaining group runs in parallel against that downloaded dist/, so the tests check the exact files the store jobs ship without building again; a failing group does not cancel the others. Store jobs wait for the build and every test job. Pull requests never publish releases or contact Mozilla or Google. Actions are pinned to commit hashes; only the release job receives repository write permission, and each store credential reaches only its own publishing job.

Pushing a tag beginning with v additionally validates that it exactly matches the numeric package, lockfile and manifest version, such as v1.0.0. After all checks pass, two store jobs run in parallel on the tested packages: the AMO job unpacks the Firefox ZIP and submits it with its source archive to addons.mozilla.org, while the Chrome job uploads the Chrome ZIP to the Chrome Web Store and submits it. The release job then creates a GitHub Release with docs/RELEASE-NOTES.md plus generated commit notes and the exact tested Chrome, Firefox and source ZIPs, plus the signed XPI when Mozilla returned one. Other tags only run checks. Failed checks, mismatched tags, a failed submission or a rejected store upload prevent the release. Existing releases are not overwritten; rerunning an already published release fails safely.

Beyond these two stores a release adds nothing: no other update channel, and the Firefox ZIP attached to it stays unsigned, since on the listed channel Mozilla signs and serves the add-on from its own listing. The release job uses GitHub's built-in token and needs no personal access token. No release is created until you push a matching version tag.

## Mozilla listing credentials

Firefox releases go to the public addons.mozilla.org listing through Mozilla's add-on submission API. Create API credentials at https://addons.mozilla.org/developers/addon/api/key/ and store them as repository secrets: AMO_JWT_ISSUER for the JWT issuer and AMO_JWT_SECRET for the JWT secret. Both are required for a tagged release; without them the submission job fails and no release is published. The secret is shown once, is tied to your AMO account, and should be revoked and replaced if exposed.

Unlike the Chrome package-upload API, the installed web-ext submission path sends the top-level AMO metadata along with the version to Mozilla's add-on endpoint. Keep summary, description and categories in amo-metadata.json current, and check the resulting developer-hub listing after submission. Screenshots and any remaining listing fields are managed in the developer hub.

Listed submissions also send amo-metadata.json, whose version object is merged into the submission payload. AMO rejects a listed version that declares no license, so version.license must stay set; it is MIT, matching the LICENSE file. The same file carries approval_notes, the build instructions Mozilla reviewers see. Listing fields such as name, summary and categories can be added there too, or set in the developer hub.

The default channel is listed: the version is submitted to the public listing under the add-on ID unqlock@fusan.me, together with artifacts/unqlock-source.zip for source review, and Mozilla signs and publishes it after review. Submission does not wait for that review, so a listed run usually returns no XPI and the release simply omits it; users install from the AMO listing. Set the repository variable AMO_CHANNEL to unlisted for self-distribution instead, which signs immediately, returns the XPI and publishes nothing on AMO.

One add-on ID can carry versions on both channels; the channel is chosen per version, and an unlisted version only needs a version number distinct from the latest listed one. Keeping the Firefox manifest in wxt.config.ts free of browser_specific_settings.gecko.update_url is what makes a self-distributed install upgradable: with no update_url, Firefox falls back to AMO's version check for unqlock@fusan.me and picks up a later approved listed version in place, preserving extension-local preferences. Adding an update_url would point those installs at that endpoint alone, and AMO rejects it on listed submissions anyway, so self-hosting updates means diverging the two channels' manifests. Mozilla documents the update_url requirement but not this fallback, which comes from AMO staff guidance, so confirm it in a disposable profile before shipping a release that relies on it.

Submit locally the same way:

```sh
npm ci
npm run build
npm run package:source
export AMO_JWT_ISSUER=...
export AMO_JWT_SECRET=...
npm run sign:firefox
```

Pass unlisted as an argument, or set AMO_CHANNEL, to override the channel. The script refuses to run without credentials, submits dist/firefox (unpacking artifacts/unqlock-firefox.zip when dist is absent), and when Mozilla returns a signed file it verifies the package's version and add-on ID and writes artifacts/unqlock-firefox-VERSION.xpi.

## Chrome Web Store credentials

Publishing uses the Chrome Web Store API, so the listing must already exist: create the item once by hand in the developer dashboard, complete its store listing and privacy fields, and note its 32-character item ID. The API updates and submits an existing item; it does not fill in listing metadata.

Enable the Chrome Web Store API in a Google Cloud project, create an OAuth client, and exchange its authorization code for a refresh token with the https://www.googleapis.com/auth/chromewebstore scope, as described at https://developer.chrome.com/docs/webstore/using-api. Request the code from https://accounts.google.com/o/oauth2/v2/auth with offline access; the older /o/oauth2/auth endpoint rejects this scope as unknown. Use a loopback redirect such as http://localhost:8818 rather than the retired out-of-band redirect, and authorize as the Google account that owns the listing.

Choose the external audience unless you have a Google Workspace organization, add that account as a test user, then publish the app so its status is in production: while it stays in testing, Google expires refresh tokens after seven days and releases start failing with an invalid_grant error. Verification is not required for this scope with a single user; the unverified-app warning appears once during authorization and is bypassed under Advanced. A production refresh token does not expire on a timer, but is invalidated by six months of disuse, by revoking it or the client secret, or by re-running the consent flow often enough to push it out of Google's hundred-token-per-client limit.

Store three repository secrets: CWS_CLIENT_ID, CWS_CLIENT_SECRET and CWS_REFRESH_TOKEN, plus the item ID as the repository variable CWS_EXTENSION_ID, since it is public listing information rather than a credential. All four values are required for a tagged release. The refresh token grants publishing rights to your developer account; revoke it in your Google account if exposed.

The default target submits to the public listing, which goes live after Google's review. Set the repository variable CWS_PUBLISH_TARGET to trustedTesters to release to testers only, or to draft to upload the new version without submitting it, which is the safest way to rehearse the credentials.

Publish locally the same way:

```sh
npm ci
npm run build
export CWS_CLIENT_ID=... CWS_CLIENT_SECRET=... CWS_REFRESH_TOKEN=... CWS_EXTENSION_ID=...
npm run publish:chrome
```

Pass trustedTesters or draft as an argument, or set CWS_PUBLISH_TARGET, to override the target. The script refuses to run without all four values, verifies the packaged manifest version against the package version, uploads artifacts/unqlock-chrome.zip and reports whether the item went live or entered review.
